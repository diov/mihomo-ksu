## 背景

`module/base.yaml` 有 14 个服务组（YouTube、Netflix、Disney、HBO、Bahamut、Bilibili、Spotify、Steam、Telegram、Google、Microsoft、OpenAI、PayPal、Apple）及对应规则，作者大部分用不到。想换成自己的服务组时，按现行合并规则（`override.md` 第 1 步，数组整体替换）只能在 override 里写出完整的 `proxy-groups`，连同 `Proxy`、`Auto` 和 5 个地区组的 `filter` 正则一起抄；base 的 `x-region` 锚点也无法跨文件引用（与 decisions #4 `x-provider-defaults` 的原因相同）。

**方向**：base 只提供基础组（`Proxy`、`Final`）和地区组；按服务分流由用户在 override 中用新的 `append-proxy-groups` 加组、用现有的 `prepend-rules` 加规则。

**否决的备选**：base 保留少量服务组（如 Google、Meta、PayPal、AI），合并规则不动。改动最小，但用户想加或换组时仍要重写整个 `proxy-groups`，问题没有解决；且哪些服务值得默认分组因人而异。

**业内做法**：Clash Verge Rev 对 `rules`、`proxies`、`proxy-groups` 都提供 prepend / append / delete 序列 [已验证 via clash-verge-rev `dev` 分支 `src-tauri/src/enhance/seq.rs`，`mod.rs` 中 `use_seq(groups, config, "proxy-groups")`，2026-11-13]。本项目只取 append，prepend / delete 出现实际需求再加。

## 1 override 追加代理组

commit：`docs(override): append-proxy-groups` → `feat(webui): merge append-proxy-groups`

**规范**（先改 `docs/override.md`）：
- 特殊键从 `prepend-rules`、`append-rules` 扩大为再加 `append-proxy-groups`；第 1 步深度合并不处理它。第 1 步"数组一律整体替换……例外只有……"一句同步加入代理组追加。
- 第 3 步"规则插入"改为"数组插入"，增加 `append-proxy-groups`：
  - 必须是数组，否则报错（复用错误码 `not-array`，`key` 为 `append-proxy-groups`）。
  - 非空时，追加到第 1 步结果的 `proxy-groups` 末尾，保持自身顺序。override 同时写了 `proxy-groups`（整体替换）时先替换再追加。
  - 第 1 步结果的 `proxy-groups` 不存在或为 `null` 时，结果就是追加的列表；是其他非数组值时报错（`not-array`，`key` 为 `proxy-groups`）。
  - 为空数组时不做任何事（与 `prepend-rules` / `append-rules` 一致）。
  - 完成后从结果中删除该键。
- 合并只检查上面两处是不是数组，不检查组条目的内容：字段是否齐全、组名是否重复（与 base 的组或追加列表内部）、`proxies` 引用的组或节点是否存在，都交给保存流程里的 `mihomo -t`（`webui/draft.js` `saveDraft`：临时配置 → 校验 → 提交 → 重载）。mihomo 拒绝重名的组，与 base 的组重名、追加列表内部重名都报 `duplicate group name` [已验证 via macOS 版 mihomo v1.19.34 `-t`，2026-11-13]。
- 追加的组是完整条目，不继承 base 的任何字段（锚点不跨文件）。
- "base 的代理组使用 `include-all`……通常不需要改 `proxy-groups`"一句改为：base 的组用 `include-all` 自动包含所有订阅的节点；要按服务分流，用 `append-proxy-groups` 加组、`prepend-rules` 加规则，不要整体覆盖 `proxy-groups`。
- 新增示例"按服务分流"（见第 2 步的 override 示例），并说明两点：
  - 服务规则一般写在 `prepend-rules`：`append-rules` 插在 `MATCH` 之前、`GEOSITE,geolocation-!cn,Proxy` 等规则之后，被这些规则先命中的流量到不了它。
  - 多个分类有重叠时，靠前的规则先命中（mihomo 自上而下匹配）。例如 `google` 引用了 `googlefcm`，要让 FCM 直连，`GEOSITE,googlefcm,DIRECT` 要写在 `GEOSITE,google,…` 之前；base 里的 FCM 直连规则排在所有 `prepend-rules` 之后，挡不住前置的 Google 规则。

**实现**：
- `webui/merge.js`：`merge()` 解构出 `append-proxy-groups`，与两个规则键一起做数组校验；深度合并之后按上面的规范生成**新数组**赋给 `out['proxy-groups']`。`deepMerge` 与 base 共享未替换的数组，而 WebUI 缓存 base（`webui/draft.js` `getBase`），不能对结果数组 `push`。
- `webui/rules.js`、`webui/changes.js` 只管规则键，不加入新键（`changes.js` 对其他顶层键整体比较计 1，`append-proxy-groups` 落在这一支，可以接受）。
- 不加 WebUI 表单，组在"高级 → 编辑 override YAML"中写。
- `test/merge.test.js`：fixture 的 `base()` 加入一个 `proxy-groups` 列表（目前没有）。测试：
  - 追加到末尾且保持顺序；先整体替换再追加；目标为 `null` 时结果为追加列表；目标为 map 时报错；空数组不改变结果；
  - 该键不出现在结果中；该键不是数组时报错；
  - 同一个 base 连续合并两次，结果相同，base 本身不变（扩展现有的"不修改输入"测试）。
- `test/rules.test.js`：`policyOptions(merge(base, override))` 包含追加的组名，即规则编辑页的策略下拉框能选到它们。

## 2 base 只保留基础组

commit：`docs: base template keeps only region groups` → `feat(config): drop service groups from the base template`

**文档**：
- `docs/decisions.md`：
  - #4 增加一条：用户加组用 `append-proxy-groups`，原因同 `x-provider-defaults`（锚点不能跨文件，整体替换要抄全部地区组）。
  - #11 增加一条"默认模板不按服务分组"：base 只有 `Proxy`、地区组、`Final`，理由同"背景"；不提供 `url-test` 的 `Auto`（按延迟自动切换会让出口节点跳动，需要时用户自己追加）；按服务分流的写法见 `override.md` 示例。
- `webui/i18n/zh.js` `subs.empty`："节点会自动出现在各地区和服务分组中"改为"……各地区分组中"。

**`module/base.yaml`**：
- `proxy-groups` 只留 `Proxy`、`HK`、`JP`、`SG`、`TW`、`US`、`Final`；删除 14 个服务组、`Auto` 和不再使用的 `x-service` 锚点，`x-region` 保留。
  - `Proxy` 只做手动选节点：去掉 `proxies`，只保留 `include-all`，不包含地区组。默认选第一个节点；没有节点时只有占位 `COMPATIBLE`（直连），见 decisions #11。
- `rules` 删除所有指向服务组的规则，剩下：

  ```
  GEOSITE,private,DIRECT
  GEOIP,private,DIRECT,no-resolve
  GEOSITE,googlefcm,DIRECT
  GEOSITE,geolocation-!cn,Proxy
  GEOSITE,cn,DIRECT
  GEOIP,cn,DIRECT
  MATCH,Final
  ```

**作者的 override**（在设备上通过 WebUI 的 YAML 编辑器**加入**现有 override，保留其中的订阅、排除应用等内容；不进仓库；也是 `override.md` 示例的原型）：

```yaml
append-proxy-groups:
  - { name: Google, type: select, proxies: [Proxy, HK, JP, SG, TW, US, DIRECT] }
  - { name: Meta,   type: select, proxies: [Proxy, HK, JP, SG, TW, US, DIRECT] }
  - { name: PayPal, type: select, proxies: [Proxy, HK, JP, SG, TW, US, DIRECT] }
  - { name: AI,     type: select, proxies: [Proxy, HK, JP, SG, TW, US, DIRECT] }

prepend-rules:
  - GEOSITE,googlefcm,DIRECT
  - GEOSITE,google,Google
  - GEOIP,google,Google,no-resolve
  - GEOSITE,meta,Meta
  - GEOIP,facebook,Meta,no-resolve
  - GEOSITE,paypal,PayPal
  - GEOSITE,category-ai-!cn,AI
```

分类内容与重叠 [已验证 via MetaCubeX/meta-rules-dat `meta` 分支 `geo/geosite/{google,meta,category-ai-!cn}.list`、`geo/geoip/facebook.list`，以及 v2fly/domain-list-community `data/google`、`data/meta`、`data/category-ai-!cn`，2026-11-13]：
- `google` 引用 `youtube`、`google-play`、`googlefcm`、`google-deepmind`（Gemini、NotebookLM、AI Studio）等。
- `meta` 引用 `facebook`、`instagram`、`whatsapp`、`messenger`、`threads`、`oculus`、`facebook-dev`，也含 `meta.ai`；`geoip:facebook` 有 121 段。
- `category-ai-!cn` 含 OpenAI、Anthropic、xAI、Perplexity、Mistral、GitHub Copilot、Cursor、Hugging Face 等，也含 `google-deepmind` 与 `meta.ai`。按上面的顺序，Gemini 走 Google，Meta AI 走 Meta（作者的选择）。
- 这些名字是 geo 数据里的分类名；`!cn` 是数据集的分类命名，不是 mihomo 运行时的取反。
- `GEOIP,…,no-resolve` 只对已经带目标 IP 的连接生效；fake-ip 下按域名发起的连接不会触发解析，所以 Google / Facebook 的 IP 规则不会抢走后面分类的域名流量 [未验证，由第 3 项真机验证中 `meta.ai`、`chatgpt.com` 的命中规则确认]。

**行为变化与对已有用户的影响**（breaking change，写进 `v0.3.0` 的 release notes）：
- 原服务组的域名改走 `geolocation-!cn → Proxy` 或 `cn → DIRECT`（如 Bilibili）。原来由 `GEOIP,telegram`、`GEOIP,netflix`、`GEOIP,google` 兜住的纯 IP 连接，没有命中剩余规则时落到 `MATCH,Final`（`Final` 默认选 `Proxy`；用户把 `Final` 改成 `DIRECT` 的，这些连接会直连）。接受这一变化。
- 只要合并后的配置里还有任何地方引用被删除的组（`prepend-rules` / `append-rules`、整体替换的 `rules`、自定义组的 `proxies`），WebUI 保存时 `mihomo -t` 报错拦下，不生成新配置。用户按 `override.md` 示例用 `append-proxy-groups` 补上组，或把引用改指向现存的组。不做自动迁移。
- 升级后的开机：有 `override.yaml`（包括空文件）时开机脚本只标记模板变更、继续运行旧 `config.yaml`，直到用户在 WebUI 保存（decisions #4）；没有 override 时直接采用新 base（`module/service.sh`），新 base 自身一致。
- `profile.store-selected` 记住的选择按组名对应：被删除的组不再出现，选择也就不起作用；`Proxy` 原来选 `Auto` 或某个地区组的，这些选项不在新 `Proxy` 里，回到默认的第一个节点；用户用同名重新追加的组（如 `Google`）可能沿用原来的选择 [未验证，不影响正确性]。

## 零上下文审查（Codex，2026-11-13，第二轮）

第一轮审的是"base 保留四个服务组"的旧方案，其中仍适用的意见（breaking change 分情况、验证用正式安装、看命中规则、补测 `meta.ai` / FCM / 保存拦截、`AGENTS.md` 索引）已并入本计划。第二轮审的是本方案删 `Auto` 之前的版本。

**必须修**（已改进计划）：
- `append-proxy-groups` 的目标为 `null`、非数组，以及空数组时的行为没有定义 → 见第 1 步规范。
- 结果数组必须新建，否则污染缓存的 base、重复追加 → 见第 1 步实现与测试。
- breaking change 的"不受影响"条件写错（整体替换的 `rules` 也可能引用旧组）→ 改为"合并后任何地方引用被删除的组都会被拦下"。
- `override.md` 第 1 步"数组例外只有……"一句、`zh.js` `subs.empty`（提到"服务分组"）漏在文件清单外 → 已加入。
- 测试 fixture 没有 `proxy-groups`；需要连续合并、`policyOptions` 的测试 → 已加入。
- 设备上的 override 应加入而不是替换整个文件 → 已注明。

**低风险**（已调整表述，不改设计）：
- "append-rules 永远命中不到"过于绝对 → 改为"被前面规则先命中的流量到不了它"。
- 删除旧 GEOIP 后的去向 → 限定为"没有命中剩余规则时"落到 `Final`。
- 重名组由 mihomo 拒绝（上游源码），不在合并中检查 → 写明边界，验证 2 实测。
- `store-selected` 的表述 → 改为按组名对应，同名组可能沿用旧选择。
- 标题"只保留地区组"不准确（还有 `Proxy`、`Final`）→ 改为"基础组"。
- 验证增加：保存被拦下后 `config.yaml` 与模板 hash 不变；无效规则通过 YAML 编辑器加入。
- 外部依据补 permalink / 内核与 geo 版本：geo 数据每日发布、内核构建时取最新（decisions #10），固定版本意义不大，只补日期。

**误报**：
- Google / Facebook 的 `GEOIP,…,no-resolve` 会抢走后面分类的域名流量：fake-ip 下按域名发起的连接不触发解析，`no-resolve` 的 IP 规则只匹配本来就带目标 IP 的连接；真机验证中 `meta.ai`、`chatgpt.com` 命中各自的 GEOSITE 规则即可确认。
- 空 `override.yaml` 的升级分支：`service.sh` 按文件是否存在判断，空文件走"标记模板变更"，与有内容时相同，无需单独处理。
