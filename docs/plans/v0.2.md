## 1 安装输出精简 `fix(module): quiet install output`

**现象**：在管理器中安装或更新模块时，终端逐个打印 zip 中每个文件的解压记录，输出很长。

**原因**：
- KernelSU、KernelSU Next、APatch 的安装器在 `customize.sh` 没有声明 `SKIPUNZIP=1` 时，用 `unzip -o "$ZIPFILE" -x 'META-INF/*' -d $MODPATH >&2` 解压整个 zip，没有 `-q`，每个文件输出一行，管理器全部显示。[已验证 via KernelSU 与 KernelSU Next `userspace/ksud/src/installer.sh`、APatch `apd/assets/installer.sh`]
- zip 共 209 个条目，其中 163 个是 metacubexd（`assets/ui/`）；它们先解压进模块目录，再由 `customize.sh` 拷到数据目录后删除。

**做法**：
- `customize.sh` 第一行写 `SKIPUNZIP=1`。安装器用 `grep -q '^SKIPUNZIP=1$'` 检测，必须独占一行、前后无空格。[已验证 via 同上]
- `customize.sh` 自己静默解压：`unzip -qo "$ZIPFILE" -x 'META-INF/*' -d "$MODPATH"`，再执行安装器原本的默认权限 `set_perm_recursive "$MODPATH" 0 0 0755 0644`，然后是现有的 `bin/mihomo` 与 `scripts/` 权限设置。
  - 这与安装器默认流程中的同一句完全相同，不属于 CLAUDE.md 禁止的"对 `$MODPATH` 执行 `chmod -R`"：webroot 的 SELinux context 由 KSU 在安装器之后处理，与改动前一致（验证时确认）。
  - 用 `ui_print` 输出用户关心的几行，代替逐文件记录（英文，与 `module.prop`、`ctl.sh` 一致）：
    1. 版本：升级时 `旧版本 -> 新版本`（旧版本取自 `/data/adb/modules/mihomo-ksu/module.prop`），首次安装只显示新版本。
    2. 随包内核版本：`bin/mihomo -v`。
    3. 数据目录新建还是保留；面板、geo 数据、API secret、`config.yaml` 各自是新装还是保留（都保留时面板与 geo 合为一行）。
    4. 新 `base.yaml` 与 `config.base.sha256` 不同且存在 `override.yaml` 时，提示重启后打开 WebUI 应用（与开机时 `description` 前缀的判断相同）。
    5. 私人 DNS 未关闭时警告（与 `ctl.sh status` 的判断相同）。
  - 否决：输出 zip 的文件数或目录清单，对用户没有意义。
- 更新 `customize.sh` 开头"在 zip 解压之后被 source"的注释。
- `SKIPUNZIP=1` 文档说明见 KernelSU `docs/guide/module.md`。[已验证]
- busybox `unzip` 支持 `-q`、`-o`、`-x`、`-d`。[未验证，实施时在设备上确认]

**否决的备选**：metacubexd 以 zip 原样随包，安装时再解压到数据目录。仍有约 45 行逐文件输出（webroot、脚本、许可证等），还要改 `build.sh`，没有解决问题。

**验证**（真机，KernelSU Next）：
- 通过管理器从 zip 安装与升级两种情况，输出只有几行进度，没有逐文件记录。
- 安装后 `ls -lZ` 对比 `bin/mihomo`、`scripts/`、`webroot/` 的权限与 SELinux context，与改动前一致。
- WebUI 能打开；重启后内核运行、fake-ip 正常；数据目录保留。

## 2 日志按天轮转 `feat(module): rotate the core log daily`

**现象**：`log/mihomo.log` 只在 `ctl.sh start` 时清空，内核开机后一直运行，文件持续增长。`log-level` 保持 mihomo 默认的 `info`，每条连接都会写一行 [已验证 via mihomo `config/config.go` 默认 `LogLevel: log.INFO`]。

**为什么不能直接删或清空**：mihomo 一直持有这个文件。`rm` 只删目录项，空间要等进程关闭文件才释放；`ctl.sh` 现在用 `>` 打开（没有 `O_APPEND`），外部截断后 mihomo 仍在原偏移处写，文件变成标称大小不变的 sparse file。

**做法**：copytruncate（logrotate 对不能重新打开日志的进程的通行做法）。
- `ctl.sh start` 改为追加打开日志（`>>`），不再在启动时清空，重启内核不丢当天的日志。
- 新增 `scripts/logrotate.sh`，由 `service.sh` 在后台启动（与 `inotifyd` 并列）：每 10 分钟比较今天的日期与 `log/day` 中记录的日期，不同时把 `mihomo.log` 复制为 `mihomo.log.1`、截断 `mihomo.log`、写入今天的日期。
  - 磁盘上最多保留当天与前一天两份。
  - 开机后循环先检查一次，关机前几天留下的日志在开机时轮转。
  - 设备深度睡眠时 `sleep` 可能被推迟，按日期比较，醒来后的第一次检查补上。
  - 复制与截断之间写入的几行会丢失，copytruncate 的已知代价，可以接受。
- WebUI 状态卡片的"最近日志"仍读 `mihomo.log`，不变。
- `date` 使用系统时区（bionic 从 `persist.sys.timezone` 读取）。[未验证，实施时在设备上确认]

**否决的备选**：
- 按大小上限轮转：用户关心的是"今天发生了什么"，按天切分更直观。若实测一天的量过大，再加大小上限。
- 写入 logcat：环形缓冲区与系统共享，会把其他应用的日志挤出去；还要加管道，`$!` 不再是 mihomo 的 pid。
- 调低 `log-level`：决定保持默认。

**验证**（真机）：
- 内核运行中，把 `log/day` 改成前一天，等待一次检查：生成 `mihomo.log.1`，`mihomo.log` 从 0 开始增长；`du` 与 `ls -l` 大小一致（没有 sparse file）。
- WebUI "重启"后 `mihomo.log` 保留之前的内容。
- 记录正常使用一天后的日志大小（只看 `du`，不打印内容，见 dev-testing.md "隐私"）。

**待办：记录一天的日志量**（第 2 步合并时尚未完成）
- 设备上的日志于 2026-10-05 约 19:40 手动轮转过一次（测试），此后正常使用。参考：开机后约 15 分钟写入约 100 KB，开机时各应用集中重连，量更大。
- 2026-10-06 起：`adb shell su -c 'du -k /data/adb/mihomo-ksu/log/mihomo.log*; cat /data/adb/mihomo-ksu/log/day'`，`day` 应为当天日期。
  - 10-06 的 `mihomo.log.1` 只覆盖 10-05 19:40 至 24:00；10-07 的 `mihomo.log.1` 才是完整的一天（10-06）。
- 把数字写进本节、更新进度表；若一天的量明显过大，与用户商量是否加大小上限（见"否决的备选"）。

## 3 排除应用

被排除的应用不走 Tun，直接使用系统网络。写入 mihomo 的 `tun.exclude-package` [已验证 via mihomo `listener/sing_tun/server.go` 传入 `ExcludePackage`]。

**两个 scope**：用户的排除列表与模块为 captive portal 排除的系统包（第 4 步）互不相干。用户列表写在 override，模块的写在 base；WebUI 只显示和编辑用户列表。

### 3.1 先行：`docs: exclude-package merges as a union`、`feat(webui): merge exclude-package as a union`
- `docs/override.md`：`tun.exclude-package` 成为数组整体替换的第二个例外，结果是 base 与 override 的并集，base 在前、去重。用户无法通过 override 去掉 base 的条目，base 中只放模块运行必需的包名，代价可以接受。
- `merge.js` 与 `test/merge.test.js`：并集、去重、只有一侧存在、override 不是数组时报错。
- 否决的备选：
  - 保持整体替换：第 4 步往 base 加包名后，任何用户排除列表都会把它们冲掉，portal 登录页又弹不出来，且用户看不出原因。
  - 表单把 base 的条目一起写进 override：模块升级后 base 新增的条目仍会被旧的完整数组覆盖。
  - 通用的数组追加语法（任意键 `append-xxx`）：目前只有这一个数组需要，属于过早抽象。

### 3.2 `feat(webui): excluded apps`
- 设计稿（链接见 `c5-webui.md` 已定事项）：画板 1 主页的"排除应用"卡片、画板 7 选择页。
- 应用列表来自 kernelsu 的 `listPackages(type)` 与 `getPackagesInfo()`（应用名、包名），经 `device.js` 调用。KernelSU、KernelSU Next、APatch 的 WebView 都实现了这两个接口 [已验证 via 三者的 `WebViewInterface.kt`，kernelsu 3.0.2 `index.d.ts`]。
  - 作者设备（KernelSU Next v3.4.0）：用户应用 87 个、系统应用 441 个；`getPackagesInfo` 取全部系统应用约 9ms [已验证 via CDP]。
  - 系统应用中约四分之一没有应用名（`appLabel` 等于包名），只显示包名一行。
  - 未安装的包名，`getPackagesInfo` 返回带 `error` 字段的对象 [已验证 via KernelSU Next 源码]，显示为"未安装"。
  - 列表取自管理器内存中的应用缓存（`SuperUserViewModel.apps`）。KernelSU Next 在 WebUI 打开时若缓存为空会在后台加载 [已验证 via `WebUIActivity.kt`]，强制停止管理器后重新打开，列表正常 [已验证 via CDP]；页面刚加载时可能还没加载完，卡片在打开后 10 秒内遇到空列表就稍后重新渲染，不把应用当作未安装。
- 图标：`<img src="ksu://icon/<包名>" loading="lazy">`。三家管理器都在 WebView 中拦截这个地址返回 PNG [已验证 via 三者的 `WebUIActivity.kt` / `WebViewHelper.kt`]；作者设备上 20 个同时加载最慢 275ms，未安装的包名立即加载失败 [已验证 via CDP]。加载失败时显示占位。
- 主页卡片：列出已排除的应用（图标、应用名、包名），与已保存版本不同的标"未保存"；底部"选择应用"进入选择页。
- 选择页：
  - 顶栏为关闭、标题、"完成"；"完成"把勾选结果写入草稿，关闭则放弃本次勾选。
  - 搜索框按应用名或包名过滤。
  - 默认只列用户应用；"系统应用"按钮切换是否同时列出系统应用（行内标"系统"），这是应用列表的常见做法。
  - 分"已排除"与"其他应用"两组，各自按应用名排序；分组在进入页面、切换系统应用时确定，勾选时不跳动。
- 修改进入草稿，与订阅、规则一样通过底部浮动条"保存并应用"；改动计数按增删的应用数计，`tun` 下的其他改动另计 1。
- 顺带统一全屏编辑页的确认按钮为"完成"（订阅页原为"确定"），单独提交 `fix(webui): one label for the editor confirm button`。
- 否决的备选：像规则那样手填包名。用户通常不知道包名，三家管理器都提供了应用列表。
- 验证（真机）：
  - 排除一个浏览器后，面板的连接列表中不再出现它的连接，其他应用照常走代理；取消后恢复；`mihomo -t` 通过；YAML 页能看到 `tun.exclude-package`。
  - 强制停止管理器后重新打开 WebUI，应用列表不为空。
  - 被排除应用的 uid 不能直接用来测（后台网络受限，连接超时）；改为排除 `com.android.shell`（uid 2000），用 `su -G 3003 2000 -c curl` 对照 root 的请求，看 mihomo 日志中有无该连接。
  - 打开系统应用后滚动流畅，图标按需加载。

## 4 Captive portal

背景与候选方案见 decisions #5。以下各项按顺序进行。

**4.1 spike（只做实验，不写功能代码）**
- 用 adb 设置 `captive_portal_http_url` / `captive_portal_https_url` 模拟 portal（做法见 decisions #5 "在家测试"），记录下面各项。实验前先记下这两个设置的原值（通常为 `null`），实验后恢复（`settings delete global <key>`），否则手机的联网检测一直异常。
  - Tun 开启和关闭两种情况下，`dumpsys connectivity` 中 Wi-Fi 网络的 capabilities（`VALIDATED` / `CAPTIVE_PORTAL`）
  - network_stack 进程的 uid
  - 关闭 tun 之后，系统需要多久重新探测；有没有办法主动触发重新评估
  - Wi-Fi 与移动数据同时在线时，各自的 capabilities 以及默认网络的切换行为（评估 watcher 是否可行的关键输入）
  - 探测域名在现有配置下的去向：`fake-ip-filter` 已有 `geosite:connectivity-check`，但解析仍走 DoH；规则上 `connectivitycheck.gstatic.com` 等会命中 `GEOSITE,google` 走代理
  - 先试 `tun.exclude-uid: [1073]`：探测请求连同它的 DNS 查询是否都不再进入 Tun，"登录网络"通知能否弹出
- 结论写进 decisions #5。

**4.2 配置层缓解**（decisions #5 方案 A）
- base 的 `tun.exclude-package` 加上 captiveportallogin 两个包名（依赖 3.1 的并集语义），登录页本身不走 Tun。
- 探测请求二选一，以 spike 结论为准：
  - 优先：base 的 `tun.exclude-uid` 加上探测进程的 uid，探测直接走系统网络，效果与 VpnService 类 App 相同，不用维护探测域名列表（各厂商的探测地址不同）。
  - 备选：探测域名设为 DIRECT + 系统 DNS，具体域名列表以 spike 的观测为准。
- 验证：模拟 portal 下能弹出"登录网络"通知。

**4.3 网络状态 watcher**（decisions #5 方案 B）
- 前提：配置层缓解经真机验证后确认不够。手机上 Wi-Fi 和移动数据常常同时在线，"当前网络是否 VALIDATED"并不等于"用户是否需要代理"，误暂停会让流量绕过代理。
- 前提事实：mihomo 的 `PATCH /configs` 支持修改 `tun`。[已验证 via mihomo `hub/route/configs.go`]
- 以下为初步设想，未经验证：
- 文件：`scripts/portal-watch.sh`，由 `service.sh` 启动
- 状态机：
  ```
  ACTIVE --(默认网络变化，且未 VALIDATED)--> PAUSED   [PATCH tun.enable=false]
  PAUSED --(VALIDATED)---------------------> ACTIVE   [PATCH tun.enable=true]
  PAUSED --(超时 N 分钟仍未 VALIDATED)------> ACTIVE   [防止一直不走代理；N 待 spike 确定]
  ```
- 事件源用 `ip monitor link address`，事件到来后查询 `dumpsys connectivity`。是否需要轮询兜底，由 spike 决定。
- 验证：在模拟 portal 下自动暂停，完成"登录"（把探测地址改回默认）后自动恢复；切换移动数据和普通 Wi-Fi 时不出现误暂停。

**4.4 真实 portal 验收**（咖啡店，一次做完）
- 连上需要认证的 Wi-Fi 后弹出"登录网络"通知，登录页能打开并完成认证。
- 认证后代理恢复，fake-ip 正常。
- 移动数据同时在线时，认证前后其他应用的流量都没有绕过代理（若有 4.3）。
- 模拟 portal 模拟不了"认证前只能用 DHCP DNS"，这一点只能在这里确认。

## 后续候选（不在 v0.2 范围内，优先级低）

- IPv6：`base.yaml` 中 `ipv6: false`，双栈网络下 IPv6 连接是被 strict-route 拦截回落 IPv4，还是绕过 Tun [未验证]。
- APatch 实测：decisions #10 中 APatch 的禁用、删除行为 [未验证]。
- 删除模块后立即停止内核：`inotify.sh` 只处理 `disable` 标记，删除后内核运行到重启为止。管理器本来就提示重启，影响小。
