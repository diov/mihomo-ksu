## 思路

1. `build.sh` 拉取 mihomo、metacubexd、geo 数据（构建时取最新版）和两个 JS 库（固定版本），与仓库里的脚本、模板、WebUI 一起打成模块 zip；版本号从 git tag 推导。
2. 设备端用 `service.sh` 以 Tun 模式启动 mihomo，home dir 为数据目录。配置文件是 `base.yaml` 与用户 `override.yaml` 的合并结果，由 KSU WebUI 生成、校验（`mihomo -t`）并热重载。
3. Captive portal 不在 v0.1 范围，优先级最低（见文末"后续候选"）。

**否决的备选**：打包 yq，让开机脚本也能合并配置（升级后无需打开 WebUI 即可生效）。否决理由：多一个约 12MB 的二进制，复杂度不值得。代价是 `base.yaml` 变化后，需要打开一次 WebUI 才能应用；开机脚本负责检测并提示（见 C3、C5）。

**复用的现有组件**：
- mihomo 的 external-ui 托管 metacubexd（面板不自己写）
- mihomo 的自更新接口（内核、面板、geo 的版本更新交给面板，见 decisions #10）
- mihomo REST API（`PUT /configs` 热重载）
- KSU/APatch 的 `webroot` 机制（不自己起 HTTP server）

## Commit 拆分

每个 commit 只有一个意图。文档、schema 与实现分开提交。

### C0 `docs: project decisions and v0.1 plan`
- 文件：`docs/decisions.md`、`docs/plans/v0.1.md`、`CLAUDE.md`、`LICENSE`、`README.md`（只写一句话简介）
- 验证：无

### C1 `build: pinned third-party versions and module packaging`
- 文件：`versions.env`、`build.sh`、`module/module.prop`、`.gitignore`（忽略 `dist/`、`.cache/`）
- 版本号：用 `git describe --tags --exact-match` 得到 `vX.Y.Z`；不在 tag 上时用 `v0.0.0-dev`。
- js-yaml、kernelsu：按 `versions.env` 固定版本下载，校验 sha256，校验失败就中止构建。
- mihomo、metacubexd、geo 数据：每次构建都从上游 latest 重新下载，不校验 sha256；下载地址与 mihomo 自更新使用的地址一致（见 decisions #10）。
- geo 数据和 metacubexd 放进 zip 的 `assets/`。
- 验证：`./build.sh` 产出 `dist/mihomo-ksu-<ver>.zip`；`unzip -l` 检查内容；`module.prop` 中的 versionCode 正确。

### C2 `feat(config): base template`
- 文件：`module/base.yaml`
- 以旧配置为参考精简，目标约 150 行：
  - 去掉内联规则，改用 GEOSITE / GEOIP（`geodata-mode: true`）
  - 代理组使用 `include-all: true` 加 `filter`（[已验证 via meta-docs example]），不再逐个引用 provider 名称
  - 不设置 `route-exclude-address`：在 Android 上排除局域网网段会让发往路由器的 DNS 绕过劫持（见 decisions #2）
  - controller 只绑定 127.0.0.1，不写 `secret`（启动时由环境变量传入）
  - `external-ui: ui`，不设置 `external-ui-name`、`external-ui-url`（默认即 metacubexd）
  - 修正 DNS 中自相矛盾的设置
- 验证：在 PC 上执行 `mihomo -t -d <home> -f base.yaml` 通过；在设备上运行后，metacubexd 中能看到所有代理组。

### C3 `feat(module): install, boot and control scripts`
- 文件：`customize.sh`、`service.sh`、`action.sh`、`scripts/env.sh`、`scripts/ctl.sh`、`scripts/inotify.sh`、`README.md`（私人 DNS 说明）
- 不需要 `uninstall.sh`：它在下次开机的 post-fs-data 阶段执行，此时内核没有运行，FORWARD 规则也不会跨重启保留，数据目录又按 decisions #6 保留，没有需要清理的东西。
- `customize.sh`：
  - 每次安装：`assets/` 中的 metacubexd 仅在数据目录的 `ui/` 不存在或为空时拷入；`GeoIP.dat`、`GeoSite.dat` 仅在数据目录中不存在时拷入；然后删除 `$MODPATH/assets`。
  - KSU 默认安装流程会在执行 `customize.sh` 前把所有文件重置为 0644 [已验证 via KernelSU `userspace/ksud/src/installer.sh`]，因此要对 `bin/mihomo` 执行 `set_perm ... 0755`。
  - 首次安装时创建数据目录、生成 `secret`，并把 `base.yaml` 拷贝成初始的 `config.yaml`（此时没有订阅，代理组只有 DIRECT），同时写入 `config.base.sha256`。
- `service.sh` 开机检测模板变更：
  - 模块内 `base.yaml` 的 hash 与 `config.base.sha256` 一致：正常启动。
  - 不一致且没有 `override.yaml`：直接用新的 `base.yaml` 覆盖 `config.yaml`，更新 hash 后启动。
  - 不一致且有 `override.yaml`：用旧的 `config.yaml` 启动，并在 `module.prop` 的 `description` 前加上提示前缀 `[Template updated: open the WebUI to apply] `（已有前缀时不重复添加）。除内核自更新外（见 decisions #10），这是模块目录中唯一允许在运行时写入的地方。
  - 启动后用 busybox `inotifyd` 监听模块目录：出现 `disable` 文件时停止内核，`disable` 被删除时启动内核，沿用旧模块的行为。KSU 本身在禁用模块时只创建标记文件，不结束进程（见 decisions #10）。
  - 不执行 `chmod -R`。
- `ctl.sh`：以 `-d /data/adb/mihomo-ksu` 和环境变量 `CLASH_OVERRIDE_SECRET="$(cat secret)"` 启动 mihomo（secret 不写入 YAML、不出现在命令行，见 decisions #7）；根据 pid 文件管理进程，不再用 `ps | grep`（内核自更新经 `syscall.Exec` 重启，pid 不变）；继续保留热点所需的 FORWARD 规则（网卡名 `Meta`，与 `base.yaml` 的 `tun.device` 一致）。
  - `status` 读取 `settings get global private_dns_mode`，值不是 `off` 时提示"私人 DNS 未关闭，可能绕过 DNS 劫持"。未设置时返回 `null`，系统按自动模式处理，同样提示。[已验证 via adb：shell 与 KSU root 均可执行；`null` 时 `dumpsys dnsresolver` 显示 Wi-Fi 为 OPPORTUNISTIC] 脚本不修改系统设置；README 补充说明。
- `action.sh`：调用 `ctl.sh` 重启内核。
- 验证（adb）：先禁用或卸载其他 Tun 模块（如旧 Clash 模块，见 decisions #2）。安装后重启手机，`ctl.sh status` 显示进程在运行；`ps` 中看不到 secret；`curl -H "Authorization: Bearer $secret" 127.0.0.1:9090/version` 能返回版本；`127.0.0.1:9090/ui` 能打开 metacubexd；在面板中升级内核后进程仍在运行，原 secret 仍可访问 API。手动修改模块内的 `base.yaml` 后重启：没有 override 时 `config.yaml` 被自动更新；有 override 时 `description` 出现提示，`config.yaml` 保持不变。Wi-Fi 与移动数据下 `ping` 域名都解析到 198.18.x.x，且 mihomo 日志中能看到该查询；临时加回局域网 `route-exclude-address` 对照一次，确认 decisions #2 的推断。在 Manager 中禁用模块后进程立即退出，启用后立即启动。

## 后续候选（不在 v0.1 范围内）

### WebUI "排除应用"
- 写入 `tun.exclude-package`。按 C4 的规则，数组会被 override 整体替换，会覆盖 base 中已有的条目（例如将来 captive portal 需要排除的包名）。实现前需要先在 `docs/override.md` 中确定数组追加语义。

### Captive portal（优先级最低）
以下各项按顺序进行，背景见 decisions #5。

**1. spike（只做实验，不写功能代码）**
- 用 adb 加 `captive_portal_http_url` 模拟 portal，记录以下内容：
  - Tun 开启和关闭两种情况下，`dumpsys connectivity` 中 Wi-Fi 网络的 capabilities（`VALIDATED` / `CAPTIVE_PORTAL`）
  - network_stack 进程的 uid
  - 关闭 tun 之后，系统需要多久重新探测；有没有办法主动触发重新评估
  - Wi-Fi 与移动数据同时在线时，各自的 capabilities 以及默认网络的切换行为（这是评估 watcher 是否可行的关键输入）
- 结论写进 `docs/decisions.md` 第 5 节。

**2. 配置层缓解**
- 方案 A：`exclude-package` 加上 captiveportallogin 两个包名；探测域名写进 `fake-ip-filter`，并设为 DIRECT + 系统 DNS。具体域名列表以 spike 的观测结果为准。
- 验证：模拟 portal 下能弹出"登录网络"通知。

**3. 网络状态 watcher**
- 前提：配置层缓解经真机验证后确认不够。手机上 Wi-Fi 和移动数据常常同时在线，"当前网络是否 VALIDATED"并不等于"用户是否需要代理"，误暂停会让流量绕过代理。
- 前提事实：mihomo 的 `PATCH /configs` 支持修改 `tun`。[已验证 via mihomo `hub/route/configs.go`]
- 以下为初步设想，未经验证：
- 文件：`scripts/portal-watch.sh`，由 `service.sh` 启动
- 状态机：
  ```
  ACTIVE --(默认网络变化，且未 VALIDATED)--> PAUSED   [PATCH tun.enable=false]
  PAUSED --(VALIDATED)---------------------> ACTIVE   [PATCH tun.enable=true]
  PAUSED --(超时 N 分钟仍未 VALIDATED)------> ACTIVE   [防止一直不走代理；N 待 spike 确定]
  ```
- 事件源用 `ip monitor link address`，事件到来后查询 `dumpsys connectivity`。是否需要轮询兜底，由 spike 决定。
- 验证：在模拟 portal 下自动暂停，完成"登录"（把探测地址改回默认）后自动恢复；切换移动数据和普通 Wi-Fi 时不出现误暂停。
